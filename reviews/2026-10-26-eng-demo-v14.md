## 차원별 평가

### E1 구조와 데이터 흐름 · 4/10
- 왜 4점인가: 흐름의 뼈대는 있다. 그룹 규칙(`SUBS`·`GPARTS`·`grpOf`, 807~830행)이 한 곳에 있고, 상세는 `judge` → `recOf`(991~1005행) 한 줄기로 흐른다. 하지만 같은 일을 하는 길이 여럿이다. 홈 추천은 `simPct`·`simFit`(1073행, 2359행)으로 따로 계산한다. 기준 옷 정하기는 `regSave`(2236행), `setBaseOk`(2123행), `pickBase`(2060행), `addToCloset`(2403행)가 각자 하고, `render()`가 그릴 때마다 `ensureBases()`를 다시 돌려 결과를 덮어쓴다(1793행). 그래서 "기준 옷이 언제 바뀌는가"를 코드 한 곳에서 알 수 없다. 주문 상태는 `delivered`·`confirmed`·`returned` 불리언 세 개다(2386행 `ordStat`). 반품했는데 확정된 상태 같은 불가능한 조합을 막지 못한다(발견 5).
- 10점이면: 등록 → 저장 → 그룹 결정 → 비교 → 추천 → 표시가 그림 한 장에 있고, 네 경로(정상·값 없음·빈 값·앞 단계 실패)마다 처리 위치가 정해져 있다. 주문은 상태 하나와 허용 전이 표로 관리하고, 기준 옷 변경은 함수 하나만 거친다.
- 근거: 데모 807~871행, 991~1005행, 1073행, 1793행, 2060·2123·2236·2386·2403행.

### E2 규칙과 예외 · 3/10
- 왜 3점인가: 정상 경로는 정해져 있지만 입력마다 그림자 경로가 비어 있다. 점검목록이 찾은 것(A1 숫자 읽기 `+값 || 0`, A3 사이즈 표기, A6 중복 등록, B2 맞는 사이즈 없음, B4 빈 칸 0 처리, B5 전부 품절)이 그대로다. 이번에 새로 찾은 예외가 둘 있다. (1) 실측이 없는 상품(p8~p11, `sizes: null`)을 사서 옷장에 담으면 치수가 모두 빈 옷이 저장된다. 그 그룹에 기준 옷이 없으면 이 옷이 기준 옷이 된다(2403~2407행). 그러면 그 그룹 모든 상품에서 차이가 전부 0이 되고, 품절 아닌 첫 사이즈가 "비슷해요"로 추천된다(1001~1004행). (2) 반품을 신청한 주문도 알림 목록에서 누르면 "구매를 확정할까요?"가 뜬다. `confirmStart`가 `returned`를 보지 않는다(2422~2428행). 확정하면 옷장 담기까지 이어져, "반품한 옷은 담지 않는다"는 확정된 결정을 깬다.
- 10점이면: 입력 칸마다 값 없음, 형식 틀림(쉼표, 단위), 범위 밖, 중복, 일부만 있음의 처리가 표로 있다. 두 번 누르기, 입력 중 나가기, 기준 옷 삭제·변경, 옷장 0벌·50벌의 동작이 정해져 있다.
- 근거: 데모 900~912행(상품 데이터), 1001~1004행, 2222~2227행(`regAdd`), 2403~2407행, 2422~2441행. 점검목록 A1·A3·A6·B2·B4·B5.

### E3 코드 품질 · 4/10
- 왜 4점인가: 좋은 점이 있다. HTML 이스케이프 함수 `esc`가 있고(721행) 검색어 등 41곳에서 쓴다. 카메라·AI 모델은 실패를 `try/catch`로 받아 수동 대안으로 보낸다(3821~3846행). 하지만 고칠 곳도 많다.
  - 같은 계산이 여러 벌이다. 차이 계산이 `recOf` 안과 `deltaOf`(1006행)에 따로 있고, 홈은 또 다른 공식(`simPct`, 5cm에서 0%, 70% 이상만 노출)을 쓴다.
  - 같은 이름의 함수가 두 번 정의돼 있다. `simFit`(1074행, 2359행), `pushOpen`(2085행, 2442행), 화면 `SCR.orders`(1776행, 2413행), `SCR.notis`(1779행, 2420행). 뒤의 것이 말없이 이긴다. 앞의 `pushOpen`은 지운 핏 화면(`go('fit')`)으로 간다. `build.py`가 네 프로토타입을 문자열 치환으로 합치면서 남은 흔적이다(점검목록 F와 연결).
  - 숫자의 근거가 없다. 가중치 1.3과 위치 기준(`i === 0 || i === 1`, 1003행), 허용 오차 `TOL = 2`(1367행), 홈의 5cm·70%(1073·1081행), 비율 채움 계수 0.21·0.33·0.43(855~857행)에 근거 주석이 없다(B1·B8).
  - 옷 이름을 이스케이프하지 않는다. `${c.name}`이 12곳, 상세의 `${base.name}`(1395행)이 그대로 `innerHTML`에 들어간다. 이름은 사용자 입력과 서버의 상품 링크 읽기(`/api/product`, 2158행)에서 온다. 점검목록 F는 "따옴표 화면 깨짐"으로 적었지만, 실제로는 외부 글자가 화면 코드로 실행될 수 있는 문제다.
  - 시연용 옷장 옷도 비율 채움을 거친다. `item()`이 `fromLegacy(x, x.m, true)`를 부른다(922행). 그래서 데모의 기준 옷도 밑단·소매부리·암홀이 추정값이다. 데모에서는 추정값끼리 비교해 결과가 실제보다 깔끔하게 보인다.
- 10점이면: 비교·추천 계산이 순수 함수 하나에 있고 홈·상세·옵션 시트·주문이 모두 그것을 부른다. 같은 이름의 정의가 없다. 숫자마다 근거나 "가정" 표시가 있다. 외부에서 온 글자는 모두 `esc`를 거친다.
- 근거: 데모 721·922·1001~1006·1073~1081·1367·1395행, 2085·2442행, 2158행. `merge/build.py` 82행(`patch miss` 확인).

### E4 실패 경로 · 3/10

### E5 확인 계획 · 2/10
- 왜 2점인가: 동작을 확인하는 테스트가 없다. `merge/build.py`에 `assert`가 있지만, 치환할 문자열이 있는지 보는 빌드 확인이다(82·185·214·236·241행). `recOf`가 맞는 사이즈를 고르는지, 품절을 빼는지는 아무도 확인하지 않는다. 그래서 "전부 품절이면 화면 오류" 같은 버그가 배포본까지 왔다. 사용성 테스트 장치는 있다. `testmode.js`가 Maze 과제용 시작 상태와 완료 코드(고른 사이즈, 비교 그림을 봤는지, 걸린 시간)를 만든다. 이것은 사람의 행동을 재는 장치이고, 계산이 맞는지 재는 장치는 아니다. 그래서 0점은 아니다.
- 10점이면: 흐름마다 정상·실패·경계값 확인이 있다. 금요일 밤에 배포해도 안심되는 확인은 "추천 정답표"다. 상품 실측과 기준 옷 쌍 20~30개에 기대 결과(추천 사이즈, 맞는 사이즈 없음, 품절, 비교 부위 부족)를 적고, 홈과 상세가 같은 답을 내는지 함께 본다. 적대적인 QA는 "56,5" 입력, 둘레 값 입력, 전부 품절 상품, 실측 없는 상품 구매 후 담기, 반품 뒤 알림 누르기, 기준 옷 삭제 직후 상세 열기를 시도한다.
- 근거: `merge/build.py`, `merge/testmode.js` 1~12행, 아래 "확인 계획" 표.

### E6 실현 가능성과 성능 · 4/10
- 왜 4점인가: 가장 어려운 부분의 시제품이 실제로 돈다. 사진 측정은 A4 기준으로 재고, 신뢰도와 예상 오차를 보여 준다. AI 모델은 미리 받아 두고(3458행) 실패하면 수동으로 넘긴다. 사이즈표 붙여넣기는 여러 표기를 읽는다. 하지만 출시 조건은 이름만 있고 값이 없다.
  - 실측 데이터 범위: 데모 상품 16개 중 4개(p8~p11)가 실측이 없다(`sizes: null`). 실제 플랫폼에서 판매처가 실측을 주는 비율, 그 값이 단면인지 둘레인지 섞인 비율은 확인하지 못했다. 이 비율이 서비스가 닿는 범위를 정한다.
  - 사진 측정 정확도: 화면에 예상 오차를 보여 주지만, 실제 옷을 손으로 잰 값과 비교한 기록은 레포에 없다. 확인하지 못함.
  - 주문 데이터 연동: 주문에는 상품과 사이즈만 남는다(2073행). 컬러·수량·추천 여부가 빠진다(E2·CEO 발견 5). `buyFlow`가 `rec`(추천 사이즈를 샀는지)를 계산해 넘기는데(1891행) `pay`가 버린다. 한 줄이면 살릴 수 있다.
  - 개인정보: 옷 치수 수집이 "선택" 동의인데 동의하지 않아도 옷장이 그대로 돈다(점검목록 E10).
  - 성능: 추천 계산은 상품 하나에 사이즈 수 × 부위 수(최대 7)라 가볍다. 대신 입력 하나에도 앱 전체를 `innerHTML`로 다시 그리고, 그때마다 `ensureBases()`가 옷장 전체를 정렬한다(1792~1793행). 옷 50벌 이상이나 목록 화면에 "내 사이즈" 배지를 켤 때(상품 수 × 사이즈 수 × 부위 수) 얼마나 느린지는 재지 않았다. 확인하지 못함. AI 모델 크기는 점검목록 기준 약 30MB다(A7).
- 10점이면: 실측 보유율, 사진 측정 오차, 주문 연동 필드, 동의 범위가 숫자나 결정으로 적혀 있고, 큰 옷장·긴 목록의 속도가 측정돼 있거나 "모름"으로 표시돼 있다.
- 근거: 데모 900~912행, 1792~1793행, 1891행, 2073행, 3458행. 점검목록 A7·E10.

## 정해야 할 것

### 결정 1. 추천 계산을 함수 하나로 모을지
- 문제: 상세(`recOf`), 차이 표시(`deltaOf`), 홈(`simPct`)이 각자 계산한다(발견 7). 결과 종류도 "사이즈 하나"뿐이라 맞는 사이즈 없음, 품절, 비교 부위 부족을 표현할 수 없다(발견 4·5·6).
- A) `recommend(상품, 기준 옷)` 하나가 사이즈, 부위별 차이, 비교한 부위 수, 상태(추천 / 맞는 사이즈 없음 / 가장 맞는 사이즈 품절 / 비교 부위 부족)를 돌려주고, 홈·상세·옵션 시트·주문서가 모두 이것만 부른다 (추천) — 노력 S~M, 위험 낮음, 유지보수 낮음(계산 한 곳)
- B) 지금 함수는 두고 홈에서 품절만 뺀다 — 노력 S, 위험 중간(다른 어긋남이 남음)
- C) 그대로 둔다 — 노력 없음, 위험 높음
- 추천 이유: "바꾸기 쉽게 먼저 만든다." 가중치·허용 오차를 v2에서 바꿀 때 한 곳만 고치고 한 곳만 확인하면 된다.

### 결정 2. 10/30 전에 추천 정답표를 만들지
- 문제: 추천을 확인하는 테스트가 없어 v1과 v2의 차이를 말로만 비교하게 된다(발견 12).
- A) 상품 실측·기준 옷 쌍 20~30개에 기대 결과를 적은 표를 만들고, 데모 안에서 한 번에 돌려 맞은 개수를 보여 주는 확인 화면(또는 콘솔 함수)을 둔다. v1·v2 모두 같은 표로 잰다 (추천) — 노력 S, 위험 낮음, 유지보수 낮음
- B) 사람이 화면을 눌러 보는 QA 시나리오 목록만 만든다 — 노력 S, 위험 중간(반복할수록 빠짐)
- C) 그대로 둔다 — 노력 없음, 위험 높음
- 추천 이유: "동작마다 그 동작이 깨지면 잡아내는 확인이 있어야 한다." 정답표는 v2의 개선을 숫자로 보여 줄 유일한 근거다.

### 결정 3. 실측 없는 상품을 산 뒤 옷장에 어떻게 담을지
- 문제: 치수가 모두 빈 옷이 기준 옷이 될 수 있다(발견 1).
- A) 실측이 없으면 "치수를 적어 주세요" 화면으로 보내고, 필수 칸(상의 총장·가슴, 하의 허리·총장)이 찰 때까지 기준 옷으로 쓰지 않는다 (추천) — 노력 S, 위험 낮음, 유지보수 낮음(등록의 `NEED` 규칙 재사용)
- B) 옷장에 담지 않고 "실측이 없어 담을 수 없어요"라고 알린다 — 노력 S, 위험 중간(옷장이 덜 참)
- C) 그대로 둔다 — 노력 없음, 위험 높음
- 추천 이유: 피해 범위가 그룹 전체라서, 입구에서 막는 비용이 가장 싸다.

### 결정 4. 주문 상태를 상태 하나와 허용 전이로 바꿀지
- 문제: 반품한 주문이 확정·옷장 담기로 갈 수 있다(발견 2·11).
- A) 상태를 `배송 중 → 배송 완료 → 구매 확정 → (옷장 담김)` / `배송 완료 → 반품 신청` 하나로 두고, 확정·반품·담기 함수가 시작할 때 현재 상태를 확인한다 (추천) — 노력 S, 위험 낮음, 유지보수 낮음
- B) 불리언은 두고 `confirmStart`·`ordAdd`에 `returned` 확인만 넣는다 — 노력 S, 위험 중간(다음 상태가 늘면 또 샘)
- C) 그대로 둔다 — 노력 없음, 위험 중간
- 추천 이유: "불가능한 전이는 이름을 붙여 막는다." 교환·자동 확정(점검목록 E3·E4)이 들어오면 불리언 조합은 더 늘어난다.

### 결정 5. 치수 검증을 한 함수로 모을지 (점검목록 A1)
- 문제: 등록, 사진 결과, 정보 수정이 서로 다른 규칙으로 숫자를 읽는다(발견 3).
- A) `readSize(부위, 입력)` 하나가 쉼표를 소수점으로 읽고, 부위별 범위와 부위 간 관계(밑위 < 총장 등)를 보고, 틀린 칸을 돌려준다. 세 화면이 모두 부른다. 범위표는 팀이 정한다 (추천) — 노력 S~M, 위험 낮음, 유지보수 낮음
- B) 등록 화면에 수정 화면의 5~200cm 검사만 복사한다 — 노력 S, 위험 중간
- C) 그대로 둔다 — 노력 없음, 위험 높음
- 추천 이유: 같은 입력에 규칙이 세 벌이면 고칠 때마다 한 벌씩 빠진다.

### 결정 6. 주문에 "추천 사이즈를 샀나"를 남길지
- 문제: 이미 계산한 `rec`를 `pay`가 버린다(발견 13). CEO 리뷰 결정 1이 요구한 측정의 출발점이다.
- A) `pay`가 주문을 만들 때 `rec`와 추천 사이즈를 함께 저장하고, 컬러·수량도 넣는다(점검목록 E2) (추천) — 노력 S, 위험 낮음, 유지보수 낮음
- B) `rec`만 저장한다 — 노력 S, 위험 낮음(금액 불일치 E2는 남음)
- C) 그대로 둔다 — 노력 없음, 위험 중간(효과 측정 불가)
- 추천 이유: 되돌리기 쉬운 한 줄 변경으로, 나중에 다시 모을 수 없는 데이터를 지금부터 남긴다.

- 먼저 찾아볼 것:

  - 사진 측정: 기준 물체로 축척을 잡는 방식이다. 알려진 함정은 원근 왜곡, 접힌 옷, 렌즈 왜곡이다. 엔진은 신뢰도와 예상 오차를 보여 주지만, 손 측정값과 비교한 기록이 없다.

```
 주문 (지금: delivered · confirmed · returned 불리언 3개)

   [배송 중] ──배송 완료──▶ [배송 완료] ──구매 확정──▶ [구매 확정] ──옷장에 담기──▶ [옷장 담김]
                                │                          │
                                └──반품·교환 신청──▶ [반품 신청됨]        └──나중에──▶ (주문 내역에서 담기)

 일어나면 안 되는 전이 (지금 막지 못하는 것에 ✗)
   ✗ [반품 신청됨] ──알림에서 구매 확정──▶ [구매 확정] ──▶ [옷장 담김]      (발견 2, 2422~2428행)
   ✓ [배송 중] ──▶ [구매 확정]            (확정 버튼이 배송 완료 뒤에만 보임, 2415행)
   ✓ [옷장 담김] ──▶ 다시 담기           (ordAdd가 inCloset 확인, 2435행)
   ✗ [구매 확정] ──▶ [반품 신청됨]       화면에는 버튼이 없지만 코드에는 막는 확인이 없음

 옷장 옷과 기준 옷

   (등록·구매 담기) ──▶ [잘 맞는 옷] ──그룹 첫 옷이거나 체크──▶ [기준 옷]
                               ▲                                 │ 삭제 → 가장 먼저 등록한 옷이 이어받음 (ensureBases)
                               └──────── 다른 옷을 기준으로 ─────┘ 종류 변경 → 그룹 이동, 원래 그룹은 이어받음

 일어나면 안 되는 전이
   ✗ 치수가 모두 빈 옷 ──▶ [기준 옷]                      (발견 1)
   ✗ 반품한 옷 ──▶ [잘 맞는 옷]                           (발견 2)
   △ 확인 없이 기준이 바뀌는 경로 4개 (등록 체크, 상세 교체, 치수 수정, 그룹 이동) (A4)
```

## 실패 경로
| 경로 | 무엇이 잘못되나 | 지금 처리 | 확인 방법 | 사용자에게 보이는 것 | 영향 범위 |
|---|---|---|---|---|---|
| 구매 → 옷장 담기 | 실측 없는 상품이 빈 치수로 담겨 기준 옷이 됨 (발견 1) | 없음 | 없음 | "기준 옷이 됐어요" 토스트, 이후 평소 같은 "S 추천" | 그 그룹 모든 상품 → **치명적 구멍** |
| 알림 → 구매 확정 | 반품한 주문이 확정·담기됨 (발견 2) | 없음 | 없음 | "내 옷장에 담았어요" | 그 그룹 추천, 확정 결정 위반 → **치명적 구멍** |
| 등록·수정 치수 | 쉼표·둘레·범위 밖 값 (A1) | 수정 화면만 5~200cm | 없음 | 필수 칸 빠짐만 토스트 | 그 그룹 모든 상품 → **치명적 구멍** |
| 비교 | 빈 칸 0 처리, 비율 채운 값 (B3·B4) | 없음 | 없음 | 실측처럼 "비슷해요" | 실측이 일부만 있는 모든 상품 → **치명적 구멍** |
| 추천 | 맞는 사이즈 없어도 추천 (B2) | 없음 | 없음 | "XL 추천" | 체형이 범위 밖인 사용자 → **치명적 구멍** |
| 추천 | 전부 품절이면 `recOf` null (B5) | 없음 | 없음 | 눌러도 반응 없음 | 그 상품의 상세·시트·구매 → **치명적 구멍** |
| 추천 | 가장 맞는 사이즈가 품절이면 말없이 차선 (B5) | 품절 제외 | 없음 | 차선이 "추천" | 그 상품 |
| 홈 추천 | 상세와 다른 공식, 품절 노출 (발견 7) | 없음 | 없음 | 홈 "32 Size"와 상세 "30 추천"이 다름 | 홈 추천 카드 전체 |
| 기준 옷 변경 | 확인 없이 바뀌는 경로 4개 (A4·발견 10) | 옷장 교체만 비교 시트 | 없음 | 토스트 일부 | 그룹 추천 전체 |
| 화면 그리기 | 외부 이름이 이스케이프 없이 들어감 (발견 9) | `esc` 있으나 이름엔 안 씀 | 없음 | 화면 깨짐 또는 코드 실행 | 그 화면, 출시 시 보안 |
| 링크 등록 | 지원 안 하는 몰·읽기 실패 (C4) | 빈 치수 화면 + 회색 안내 | 없음 | 12px 회색 글씨 | 등록 이탈 |
| 사진 측정 | 지원 안 하는 그룹·인식 실패 (C1) | 원인별 점검 목록, 수동 대안, 신뢰도 표시 | 없음 | 보임 | 그 옷 한 벌 |

치명적 구멍(처리 없음 + 확인 방법 없음 + 사용자에게 안 보임): 6개. 새로 찾은 것 2개(발견 1·2), 점검목록에 있지만 확인 계획이 없는 것 4개(A1, B3·B4, B2, B5). 점검목록의 "정할 것"과 F의 "버그를 고칩니다"는 확인 방법이 아니라서 구멍으로 셌다. CEO 리뷰의 "추천 정확도 신호 없음"은 측정 문제라 여기서는 결정 6으로만 다뤘다.

## 확인 계획
| 흐름 | 정상 확인 | 실패 확인 | 경계값 확인 |
|---|---|---|---|
| 추천 계산 (`recOf` → 결정 1의 함수) | 정답표 20~30쌍에서 기대 사이즈와 일치 | 전부 품절 → "추천할 수 없어요", 맞는 사이즈 없음 → 별도 상태 | 동점 두 사이즈, 차이 정확히 2cm, 비교 부위 1개뿐 |
| 홈 추천 | 홈 카드 사이즈 = 상세 추천 (데모 데이터 전체 쌍) | 품절 사이즈가 홈에 안 뜸 | 70% 바로 위·아래 상품 |
| 직접 입력 등록 | 필수 칸만 채워 등록 → 기준 옷 됨 | "56,5", "56cm", 음수, 560 → 칸 표시와 함께 막힘 | 밑위 > 총장, 둘레 값(단면의 2배) |
| 구매 → 확정 → 담기 | 배송 완료 → 확정 → 담기 → 상세에서 비교됨 | 반품 신청 뒤 알림 누르기 → 확정 불가 | 실측 없는 상품 구매 후 담기, 같은 주문 두 번 담기 |
| 기준 옷 변경·삭제 | 옷장에서 교체 → 비교 시트 → 추천 다시 계산 | 기준 옷 삭제 직후 상세 열기 | 그룹 마지막 옷 삭제, 종류 변경으로 그룹 이동 |
| 상세 상태 분기 | 6가지 상태(비로그인~비교 완료) 각각 안내 | 실측 없는 상품 → 대안 안내 | 같은 그룹 없음 vs 옷장 빔 문구 구분 (B12) |
| 화면 안전 | 일반 이름 표시 | 이름에 `<`, `"` 넣어 등록 → 글자 그대로 보임 | 아주 긴 이름(50자) |
| 사진 측정 | 상의·바지 A4 촬영 → 손 측정과 비교 기록 | 카메라 거부, 모델 다운로드 실패 → 수동 대안 | 반팔·치마·롱아우터 (C1) |

금요일 밤 배포 기준: 위 표의 첫 두 줄(추천 정답표, 홈·상세 일치)이 모두 통과해야 한다. 나머지는 사용성 테스트(`testmode.js`) 전에 사람이 한 번씩 눌러 보는 QA 목록으로 쓴다.
