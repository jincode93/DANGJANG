# DANGJANG 평가 루브릭

결과물(데모, PRD, 정책 문서, 확장 기능 프로토타입)을 CEO, 디자이너, 엔지니어 세 관점에서 각각 100점 만점으로 채점한다.
리뷰 스킬(`/review-ceo`, `/review-design`, `/review-eng`)이 이 문서를 기준으로 쓴다. 기준을 바꾸면 날짜와 이유를 맨 아래 변경 기록에 남긴다. 기준이 바뀐 뒤의 점수는 이전 점수와 바로 비교하지 않는다.

## 점수 매기는 법

관점마다 항목 5개, 항목당 20점이다.

| 점수 | 뜻 |
|---|---|
| 20 | 이대로 출시해도 된다. 예외 상황까지 정해져 있다 |
| 15 | 대부분 됐다. 작은 구멍이 1~2개 있다 |
| 10 | 기본 흐름(행복한 경로)만 된다. 예외 상황은 비어 있다 |
| 5 | 생각은 있지만 화면이나 문서에 드러나지 않는다 |
| 0 | 없다 |

- 중간 점수(예: 12, 17)도 쓸 수 있다.
- **근거 규칙:** 점수마다 근거를 붙인다. 화면 이름, 파일 경로, 문서의 절 같은 것이다. 근거를 대지 못하면 그 항목은 10점을 넘을 수 없다.
- **증거 수준:** 데모에서 직접 확인한 것과 문서만 보고 추정한 것을 구분해 적는다.
- **판정:**
  - 80점 이상: 진행
  - 60~79점: 고치고 진행
  - 60점 미만: 방향 재검토
- **종합 점수:** 세 관점 점수의 평균.

## CEO 관점: 이게 사업이 되나

참고: gstack `plan-ceo-review`의 전제 의심, 12개월 뒤 그림, 범위 판단

| 항목 | 20점이면 | 확인할 것 |
|---|---|---|
| C1. 문제의 크기와 근거 | 타깃의 문제가 실제 데이터로 증명되고, 얼마나 자주·크게 아픈지 숫자로 말할 수 있다 | 설문·인터뷰 수치, 실패 빈도, 반품 경험 |
| C2. 차별점 | 지금 대안(체형 필터, 실측표, 쇼핑몰의 구매내역 기반 사이즈 비교)보다 나은 점이 한 문장으로 설명되고 데모에서 바로 보인다 | 포지셔닝 문장, 상품 상세의 비교 화면 |
| C3. 사업 효과 | 이 기능을 도입한 패션 커머스 입장에서 무엇이 좋아지는지(사이즈 반품 감소, 구매 전환, 재방문) 지표로 정의돼 있고, 측정 방법이 있다 | 북극성 지표, 보조 지표, 측정 시점 |
| C4. 범위 판단 | 지금 범위가 핵심 문제에 집중돼 있고, 뺀 것마다 이유와 다시 다룰 시점이 있다 | 결정 기록, 로드맵 |
| C5. 12개월 뒤 그림 | 이 기능이 커지면 무엇이 되는지, 다음 단계가 지금 구조 위에 올라갈 수 있는지 설명된다 | 로드맵, 확장 기능과 메인 기능의 연결 |

CEO가 꼭 묻는 질문:
- 이 문제를 안 풀면 패션 커머스는 무엇을 잃나? (반품 비용, 이탈, 구매 포기)
- 사용자가 첫 옷 1벌을 등록할 이유가 충분한가?
- 이걸 더 작게 만들어도 가치가 전달되나? 아니면 더 크게 가야 의미가 있나?

## 디자이너 관점: 쓰는 사람이 바로 이해하나

참고: gstack `plan-design-review`의 상태 설계, 정보 위계, 구체적 선택

| 항목 | 20점이면 | 확인할 것 |
|---|---|---|
| D1. 첫 사용 흐름 | 기준 옷이 0벌인 사람이 왜 등록해야 하는지 알고, 첫 1벌을 막힘 없이 등록해 첫 비교 결과까지 간다 | 온보딩, 등록 4가지 경로, "잘 맞는 옷만" 규칙 안내 |
| D2. 결과의 이해 쉬움 | 상품 상세에서 "이 사이즈가 나에게 어떤지"를 3초 안에 알 수 있고, 가장 큰 차이가 먼저 보인다 | 추천 사이즈, 부위별 차이, 도식, 표현 용어 |
| D3. 상태 설계 | 빈 상태, 오류, 로딩, 품절, 비교할 수 없음, 기준 옷 없음마다 무엇을 보여주고 사용자가 무엇을 할 수 있는지 정해져 있다 | 각 상태의 화면과 문구 |
| D4. 일관성 | 용어, 색의 뜻, 버튼, 컴포넌트가 상세 시안 기준으로 화면마다 같다 | 커요/넉넉해요 같은 용어, 초록의 의미, 주 버튼 |
| D5. 입력 편의와 접근성 | 치수 입력이 쉽고 실수를 바로 알려주며, 글자 크기·대비·터치 영역·라벨이 기준을 지킨다 | 직접 입력 화면, 오류 표시, 12px 이하 글자 |

디자이너가 꼭 묻는 질문:
- 이 화면에서 사용자가 가장 먼저 봐야 하는 것은 무엇이고, 실제로 그게 가장 먼저 보이나?
- 일이 잘못됐을 때 사용자는 무엇을 보고, 다음에 무엇을 할 수 있나?
- 같은 뜻을 화면마다 다른 말이나 다른 색으로 쓰고 있지 않나?

## 엔지니어 관점: 만들 수 있고, 틀리지 않나

참고: gstack `plan-eng-review`의 엣지케이스, 실패 경로, 테스트 가능성

| 항목 | 20점이면 | 확인할 것 |
|---|---|---|
| E1. 데이터 규칙의 명확성 | 기준 옷, 그룹, 세부 종류, 치수 칸의 규칙이 문서로 정해져 있고 화면 동작과 일치한다 | 그룹 8개 규칙, 기준 옷이 바뀌는 모든 경로 |
| E2. 엣지케이스와 실패 경로 | 잘못된 입력, 중복 등록, 부분 반품, 교환, 품절, 데이터 없음에서 무엇이 일어나는지 정해져 있다 | 출시 수준 점검 목록의 ★★★ 항목 |
| E3. 추천 로직의 타당성 | 가중치, 허용 오차, 작은 쪽과 큰 쪽의 차이, 확신 정도에 근거가 있고, 맞는 사이즈가 없을 때를 처리한다 | 현재 추천 로직, B1~B9 |
| E4. 실현 가능성 | 실측 데이터 확보, 사진 측정, 쇼핑몰 상품·주문 데이터 연동의 제약과 대안이 정리돼 있다 | 판매처 실측표 비율, 사진 측정 지원 그룹 |
| E5. 검증 가능성 | QA 시나리오가 있고, 지표를 계산하는 데 필요한 이벤트가 정의돼 있다 | 테스트 시나리오, 로그 이벤트 목록 |

엔지니어가 꼭 묻는 질문:
- 기준 옷에 잘못된 값이 하나 들어가면 어디까지 틀어지나?
- 데이터가 없는 칸은 비교에서 어떻게 다뤄지나? 0으로 들어가지 않나?
- 이 동작이 맞다는 걸 무엇으로 확인하나?
