# 신기능 제안

새 기능 아이디어를 제안하는 곳이다. 정책 문서에는 확정된 규칙만 두므로, 아직 합의되지 않은 기능은 여기에 둔다. 합의되면 정책(`docs/policy/`)으로 옮긴다.

## 만드는 법

1. 제안마다 새 파일을 하나 만든다. 파일 이름은 `기능이름.md` (예: `코디-추천.md`).
2. 아래 양식을 복사해서 채운다.
3. PR로 올린다. 다른 사람의 제안 파일은 고치지 않는다. 의견은 그 기능의 이슈에 댓글로 남긴다.
4. PR을 올리면 자동 검토가 사업·디자인·개발·정책 네 관점으로 돈다(기준: `docs/eval/proposal-rubric.md`). 전체 검토는 기능마다 하나인 이슈 `[신기능] 기능이름`에 쌓이고, PR에는 판정과 이슈 링크만 달린다. 머지 뒤에 고치는 PR도 같은 이슈에서 검토가 이어진다. 의견은 그 이슈에 남긴다. 올리기 전에 미리 보려면 Claude Code에 "`/review-proposal docs/proposals/기능이름.md`"라고 말한다. 검토는 조언이고, 결정은 사람이 한다. 이미 열린 PR을 다시 검토하려면 Claude Code에 "PR N번 제안서 자동 검토 다시 돌려 줘"라고 말한다(`gh workflow run proposal-review.yml -f pr=N`).

## 양식

칸 이름 옆의 번호는 자동 검토 항목이다(B 사업, X 디자인, T 개발, L 정책. `docs/eval/proposal-rubric.md`). 모르는 칸은 비우지 말고 "모름"이나 "확인할 것"이라고 적는다. 비어 있으면 검토가 빠뜨린 것으로 본다. 검토 항목은 모두 이 양식에 칸이 있다. 검토 항목을 바꾸면 이 양식도 같은 PR에서 고친다. 빠지면 PR 검사(`제안서 양식 검사`)가 실패한다.

```markdown
# 기능 이름

- 제안한 사람:
- 날짜:
- 프로토타입: (있으면) `prototype/public/features/기능/` · 데모에서 오른쪽 "신기능" 패널의 토글로 켜서 본다

## 어떤 문제를 푸나요? (B1)
누가, 언제, 얼마나 자주, 무엇 때문에 불편한지. 근거 파일(리서치, 인터뷰, 멘토링)을 붙이고, 근거가 없으면 "가정"이라고 적는다.

## 어떻게 푸나요?
기능을 한두 문단으로. 범위 밖인 것도 적는다.

## 어디서 만나나요? (X1, X2, X3)
사용자가 이 기능을 처음 만나는 곳(홈, 상품 상세, 장바구니, 주문 완료, 옷장, 알림)과 그때 하던 일. 사용자가 들이는 수고(등록, 입력, 촬영)와 처음 얻는 것.
기존 화면에 들어가면 무엇이 밀려나나. 상품 상세라면 사이즈 판정과 구매 버튼이 그 자리에 그대로 있나.

## 상태마다 무엇을 보나요? (X4)
해당하는 것만 한 줄씩. 빈 화면에는 "없음" 대신 다음에 할 일을 적는다.
- 비회원:
- 옷장 0벌, 옷 1~2벌:
- 기준 옷 없음:
- 실측이 없는 상품, 사이즈 품절:
- 불러오는 중, 실패:

## 옷장을 어떻게 키우나요? (B3)
이 기능 때문에 사람들이 옷장을 더 채우나, 더 자주 쓰나.

## 왜 지금, 얼마나 작게? (B5)
- 지금 해야 하는 이유: (다른 기능보다 먼저인 이유. 옷장을 키우지 않는 기능이면 꼭 적는다)
- 같은 가치를 내는 가장 작은 버전:
- 이번에 하는 것 / 미루는 것 / 하지 않는 것:
- 시즌(SS·FW 바뀔 때, 큰 세일)이 출시나 검증에 주는 영향:

## 무엇이 좋아지나요? (B2)
지표 경로 한 줄. 단계마다 지표 이름을 붙인다.
예: 패션북 만들기(만든 수) → 옷 등록(등록 수) → 상품 상세 비교(비교 사용 수) → 구매(전환·반품)
어디에 보이나: 상품 상세처럼 거의 모든 구매자가 지나는 곳인가, 옷장 안쪽처럼 일부만 보는 곳인가.
숫자는 근거가 있을 때만 쓴다. 없으면 "확인할 것".

## 얼마나 드나요? (T1, T2, T3, X6, B4)
- 규모: S / M / L, 그 이유 (화면 몇 개, 새 대상 몇 개, 연동)
- 가장 불확실한 기술 가정과 미리 확인하는 법: (예: 사진 실측 정확도 → 옷 5벌로 줄자와 비교, 오차 2cm 안이면 통과)
- 필요한 데이터: (예: 상품 실측, 브랜드 정보) 지금 얼마나 있나, 없으면 누가 채우나
- 바뀌는 기존 구조: (옷장, 기준 옷, 비교 계산, 주문 상태 중 무엇이 바뀌나. 없으면 "없음")
- 디자인 시스템: 있는 토큰과 `.dj-*` 컴포넌트로 되나. 새 컴포넌트가 필요하면 이름과 이유
- 입점 브랜드가 더 할 일과 얻는 것: (없으면 "없음")

## 어떻게 내놓고 끄나요? (T6)
- 신기능 토글로 켜고 끌 수 있나:
- 상품 상세에 들어가면 화면이 느려지나: (모르면 "확인할 것")
- 잘못 돌 때 팀이 어떻게 알아채고 끄나:

## 지금 정책과의 관계 (L1, L2, L5)
- 기대는 정책: (예: BASE-02, REC-06) 그 정책의 문장을 함께 적는다
- 부딪히는 정책과 어떻게 할지: (예: REC-05 퍼센트 금지 → 사이즈 판정으로 바꾼다). 없으면 "없음"
- 새로 필요한 용어:
- 새로 생기는 대상과 상태: (예: 패션북: 만드는 중 → 저장 → 공유. 일어나면 안 되는 전환도). 기존 대상(옷장, 기준 옷, 비교, 회원)에 주는 영향. 없으면 "없음"
- 보여 주는 숫자와 문구: 숫자마다 출처, 단위(단면·둘레), 반올림. 판정 낱말은 REC-04·REC-05를 따르나. 데이터가 없을 때 무엇을 보여 주나

## 이럴 땐 어떻게 하나요? (L3, L4)
해당하는 것만 적는다. 정하지 못했으면 "정하지 않음"이라고 적는다.
- 옷을 지우거나 고치면, 탈퇴하면:
- 반품·교환, 구매 확정 전후:
- 품절·단종, 사이즈 표기가 섞인 상품(S/M/L, 95, 26, FREE):
- 비회원이 보면, 공유받은 사람이 보면:

## 잘못되면 무엇을 잃나요? (T5, X5, L6)
해당하는 것마다 대응을 적는다. 해당 없으면 "없음".
- 개인정보: (치수, 사진, 공유 링크, 구매내역) 왜 받나, 언제 동의받나, 얼마나 두고 어떻게 지우나
- 사용자 신뢰: (잘못된 판정, 틀린 추천) 사용자가 "왜 이렇게 나왔는지" 볼 수 있나
- 입점 브랜드:
- CS: "추천대로 샀는데 안 맞아요"에 뭐라고 답하나, 반품 배송비는 누가 내나
- 사람이 하는 일: (템플릿 제작, 신고 확인 등) 누가, 얼마나 자주

## 어떻게 검증하나요? (B6, T4)
- 가장 위험한 가정: (이 기능이 정말 가치가 있다는 근거가 되는 가정 하나)
- 가치 합격선: 실행 전에 숫자로. (예: 써 본 참가자 10명 중 6명 이상이 옷을 1벌 더 등록한다)
- 사용성 합격선: 있으면. (예: 10명 중 7명 이상이 도움 없이 저장까지 끝낸다)
- 통과하면:
- 실패하면:
- 어떻게 재나요: (어떤 행동이 기록되어야 하나. 예: 패션북 저장, 공유 링크 열기)

## 아직 모르는 것
```

이미 올린 제안서는 새 양식으로 다시 쓰지 않아도 된다. 검토에서 "이것만 채우면"으로 짚은 칸만 더하면 된다.
