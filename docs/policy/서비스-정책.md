# DANGJANG 서비스 정책

DANGJANG이 어떻게 동작해야 하는지를 한곳에 모은 문서다. 기획, 디자인, 개발, 리뷰가 모두 이 문서를 기준으로 삼는다. 데모가 이 문서와 다르면 데모를 고친다.

- 기준일: 2026-10-27
- 근거: `logs/decision-log.md`, 세 관점 리뷰(`reviews/2026-10-26-*-demo-v14.md`), 출시 수준 점검 목록(`reviews/2026-10-26-출시수준-점검목록.md`), 멘토링 기록
- 추천 규칙을 정할 때 검토한 선택지: `docs/policy/결정지-2026-10-26-추천규칙.md`

## 상태 표시

| 표시 | 뜻 |
|---|---|
| ✅ 확정 | 팀이 정했다. 날짜와 근거가 있다 |
| 🟡 추천안 | 리뷰나 멘토링에서 나온 추천. 팀 확인 전이다 |
| ⬜ 미정 | 아직 정하지 않았다. 선택지만 있다 |
| ⛔ 흉내만 | 발표 범위에서는 화면만 보여 주고 실제 규칙은 정하지 않는다 |

## 0. 원칙

모든 규칙은 아래 원칙을 따른다. 규칙이 없는 상황을 만나면 원칙으로 판단한다.

1. **정확하지 않으면 정확하지 않다고 말한다.** 추정값, 부족한 데이터, 애매한 추천은 화면에 그대로 드러낸다. 틀린 확신보다 "모른다"가 신뢰를 덜 잃는다.
2. **조용한 실패는 없다.** 잘못된 입력, 품절, 비교 불가는 사용자에게 보이고, 다음에 할 일을 알려 준다.
3. **사용자가 입력한 정보만 쓴다.** 사용자가 직접 넣지 않은 신체·옷 정보는 가져오지 않는다.
4. **수고보다 쓸모를 먼저 보여 준다.** 사용자는 쓸모가 보일 때만 정보를 입력한다(인터뷰 5/5).
5. **한 뜻은 한 말과 한 색으로.** 같은 판정을 화면마다 다른 단어나 색으로 말하지 않는다.

## 2. 옷장 등록

### 2.1 무엇을 등록하나

- ✅ **잘 맞는 옷만 등록한다.** 등록할 때 핏을 묻지 않는다. 안 맞는 옷 관리 기능은 두지 않는다. (10/22, 멘토링 4회차)
- ✅ **이 규칙을 사용자에게 알린다** (C2, 10/27). 첫 등록 화면과 옷장 빈 상태에 "잘 맞아서 자주 입는 옷을 넣어 주세요"를 보여 준다. 이미 넣은 옷을 빼는 방법은 삭제로 충분하다.

### 2.2 등록 경로

| 경로 | 정책 | 상태 |
|---|---|---|
| 구매 확정 | 배송 완료 → 구매 확정 → "옷장에 담을까요?" [나중에 / 담기]. 주문 내역에서도 담을 수 있다 | ✅ 10/22 |
| 상품 링크 | 판매처 실측을 가져온다. 실패하면 실패 이유를 보여 주고, 사이즈표 붙여넣기와 직접 입력을 버튼으로 권한다. 지원 쇼핑몰 목록은 보여 주지 않는다 (C4) | ✅ 10/27 |
| 구매내역 캡처 | 캡처에서 상품을 찾아 실측을 가져온다. 못 찾으면 링크 실패와 같은 방식으로 안내한다 (C7) | ✅ 10/27 |
| 사진 촬영 | 아래 2.3 | ✅ 10/27 |
| 직접 입력 | 핵심 부위는 필수, 나머지는 선택. 사이즈표 붙여넣기를 지원한다 | ✅ |

### 2.3 사진 측정

- ✅ **지원 범위를 긴팔 상의와 긴바지로 좁힌다** (C1, 10/27). 지금 엔진은 상의와 바지만 재고, 반팔·치마·롱아우터에서는 부위가 비거나 범위 밖으로 나온다. 다른 그룹은 사진 촬영 입구에서 "이 종류는 직접 입력해 주세요"로 안내한다.
- ✅ **발표에서 사진 측정을 핵심 기능으로 내세우지 않는다** (10/27). 보조 등록 수단으로 소개한다. 멘토는 3~4cm 오차가 신뢰를 깎고 구현 리소스가 크다며 우선순위에서 빼라고 했다(멘토링 3회차). 대안으로 "AI가 먼저 대략적인 값을 보여 주고, 담당자가 정해진 기간 안에 정확한 값으로 바꾼다"는 운영 방식을 로드맵에 둔다. 인건비 계산이 필요하다.
- ✅ 측정에 실패하면 숫자를 지어내지 않고, 원인과 수동 대안을 보여 준다 (이미 그렇게 동작함).

### 2.4 치수 입력 검증

- ✅ **검증은 한 곳에서 한다** (A1, 10/26). 등록, 사진 결과, 정보 수정이 같은 검증을 쓴다.
- ✅ 쉼표는 소수점으로 읽는다. "56cm"처럼 단위가 붙은 값도 읽는다.
- ✅ 부위별 범위와 부위 간 관계(밑위 < 총장, 허리 < 엉덩이)를 본다. 틀리면 **저장을 막고**, 그 칸 테두리와 칸 아래 글자로 이유를 보여 주고, 첫 오류 칸으로 이동한다.
- ⬜ 부위별 범위 값. 데모 상품 실측 분포로 초안을 만든 뒤 팀이 확인한다.
- ⬜ 둘레로 보이는 값(단면의 2배 근처)을 반으로 나눠 줄지.

### 2.5 실측 없는 옷

- ✅ **실측 없는 상품을 사서 담을 때는 "치수를 적어 주세요" 화면으로 보낸다.** 핵심 부위가 찰 때까지 기준 옷으로 쓰지 않는다. (10/26, 엔지니어 리뷰에서 찾은 버그)

### 2.6 치수 출처

- ✅ **치수 출처(판매처 실측 / 내가 잰 값)를 화면에서 구분하지 않는다** (C5, 10/27). 추정값만 따로 표시한다(4.3).
- ⬜ 출처별로 오차를 다르게 둘지.

### 2.7 그 밖의 등록 규칙

- ✅ 세부 종류를 고르지 않으면 어느 그룹으로 비교되는지 표시한다. 예: "긴팔 상의로 비교해요" (D2, 10/27). 세부 종류는 필수가 아니다.
- ✅ 종류를 바꿔도 같은 부위 값은 유지한다 (D3, 10/27).
- ⬜ 중복 등록: 무엇을 같은 옷으로 볼지, 막을지 알리기만 할지 (A6).

## 3. 기준 옷

- ✅ **그룹마다 기준 옷은 하나다.** 다른 그룹 옷끼리는 비교하지 않는다. (10/26)
- ✅ 그룹의 첫 옷이 자동으로 기준 옷이 된다. 단, 핵심 부위가 없는 옷은 기준 옷이 될 수 없다(2.5).
- ✅ **기준 옷과 비교 옷은 다른 개념이다** (10/27). 기준 옷은 그룹의 모든 추천에 쓰이는 옷이고, 비교 옷은 지금 보고 있는 상품 하나와 견줘 보는 옷이다. 비교 옷을 바꿔도 기준 옷은 바뀌지 않는다.
- ✅ **상품 상세의 "교체하기"는 비교 옷만 바꾼다** (A4·B13, 10/27). 이 상품에서만 고른 옷과 비교하고, 다른 상품의 추천은 그대로다.
- ✅ **내 옷장 > 옷 상세에서는 기준 옷을 바꿀 수 없다** (10/27). "기준 옷 바꾸기"를 없앤다.
- ✅ **기준 옷이 바뀌는 경로에서는 확인을 받는다** (A4, 10/27). 대상: 등록 때 "기준 옷으로" 체크, 기준 옷 치수 수정, 종류 변경으로 그룹이 바뀌는 경우. 확인창에는 치수 차이를 보여 준다.
- ✅ **등록한 뒤 기준 옷은 내 옷장 목록에서 바꾼다** (10/27). 목록에서 그룹별로 기준 옷을 고르는 곳을 둔다. 바꿀 때는 확인창에 지금 기준 옷과 새 기준 옷의 치수 차이를 보여 주고, 바꾼 뒤에는 실행 취소 토스트로 되돌릴 수 있게 한다. 기준 옷을 바꾸는 곳은 이곳과 등록 때 체크 두 곳뿐이다.
- ⬜ 기준 옷을 지웠을 때 누가 이어받나: 등록 순 / 치수가 가장 가까운 옷 / 사용자 선택 (A4).
- ✅ 옷 삭제와 기준 변경은 실행 취소 토스트로 되돌릴 수 있게 한다 (A5, 10/27).
- ✅ **그룹별 기준 옷 현황은 상품 상세에서만 알린다** (D1, 10/27). 예: 반팔 상품에서 "반팔 기준 옷이 없어요". 내 옷장에 그룹 8개 현황판은 두지 않는다. 내 옷장 목록의 기준 옷 고르기는 옷이 있는 그룹만 보여 준다.

## 4. 사이즈 비교와 추천

모두 ✅ 확정 (10/26). 검토한 선택지는 결정지에 있다.

### 4.1 계산 구조

- 추천 계산은 함수 하나(`recommend(상품, 기준 옷)`)가 맡는다. 홈, 상품 상세, 옵션 시트, 주문서가 모두 이것만 쓴다.
- 결과는 사이즈, 부위별 차이, 비교한 부위 수, 상태를 함께 돌려준다.

### 4.2 추천 상태

| 상태 | 언제 | 화면 문구 예시 |
|---|---|---|
| 추천 | 아래 어느 것에도 해당하지 않을 때 | "M 추천" |
| 두 사이즈 사이 | 1·2위 점수 차이가 작을 때 (초안: 10% 이내) | "M과 L 사이예요 · M은 기장이, L은 가슴이 맞아요" |
| 맞는 사이즈 없음 | 가장 가까운 사이즈도 핵심 부위 중 하나가 4cm를 넘게 **작을 때** | "맞는 사이즈가 없어요 · 가장 가까운 L도 가슴이 5cm 작아요" |
| 가장 맞는 사이즈 품절 | 1위 사이즈가 품절일 때 | "가장 잘 맞는 M은 품절이에요 · 다음은 L" |
| 모든 사이즈 품절 | 모든 사이즈가 품절일 때 | "모든 사이즈가 품절이에요" |
| 비교 부위 부족 | 두 옷 모두 잰 핵심 부위가 2개 미만일 때 | "비교할 치수가 부족해요" |

크기만 큰 경우는 "맞는 사이즈 없음"이 아니다. 추천하되 "넉넉해요"를 보여 준다.

### 4.3 비교 규칙

| 규칙 | 내용 |
|---|---|
| 비교 대상 | 두 옷 모두 잰 부위만 비교한다. 빈 칸은 0으로 넣지 않고 점수에서 뺀다 |
| 추정값 | 추천 점수에서 뺀다. 도식에는 점선으로 그리고 "추정"이라고 표시한다 |
| 최소 부위 | 핵심 부위 2개가 모두 있어야 추천한다 |
| 가중치 | 부위 이름에 붙인다. 품 부위 1.3, 길이 부위 1.0 (초안) |
| 작은 쪽 | 품 부위에서 작은 쪽 차이를 1.5배로 본다. 길이 부위는 같게 본다 (초안) |
| 허용 오차 | 2cm 이내면 "비슷해요", 4cm를 넘으면 "커요·작아요". 10/30까지 유지하고, 정답표 결과를 보고 v3에서 부위별 값을 정한다 |
| 핏 의도 | 오버핏·신축성은 추천에 반영하지 않는다. 오버핏 상품에는 "오버핏이라 크게 나오는 옷이에요"를 안내한다 |
| 후기 | 후기는 추천에 반영하지 않는다 (B14, 범위 밖) |

"(초안)" 값은 근거가 아직 없다. 정답표(4.4)의 맞은 개수를 보고 조정하고, 조정하면 이 문서와 결정 기록을 함께 고친다.

### 4.4 정답표

- 상품 실측·기준 옷 쌍 20~30개에 기대 결과(사이즈와 상태)를 적는다.
- 데모 안의 확인 함수로 한 번에 돌려 맞은 개수를 본다.
- v1과 v2를 같은 표로 잰다. 규칙을 바꿀 때마다 다시 돌린다.

### 4.5 홈의 옷장 기준 추천

- 상세와 같은 함수를 쓰고 품절 사이즈를 뺀다.
- 퍼센트("92% 비슷해요")는 쓰지 않는다. 종합 판정 단어로 보여 준다.
- ⬜ 결과가 없을 때 기준을 완화할지, "전체보기"를 전용 목록으로 보낼지 (E13).

## 5. 표현

### 5.1 판정 용어 ✅ (10/26)

| 층 | 쓰는 말 |
|---|---|
| 종합 판정 | 비슷해요 / 커요 / 작아요 |
| 길이 부위 | 길어요 / 짧아요 |
| 품 부위 | 넉넉해요 / 타이트해요 |

"넓어요", "딱 맞아요", 퍼센트는 쓰지 않는다.

### 5.2 비교 도식 ✅ (10/26)

- 어느 옷인지는 선 모양으로만 구분한다. 내 옷은 회색 점선, 상품은 검정 실선.
- 얼마나 다른지는 뱃지 색으로만 보여 준다. 가장 큰 차이의 뱃지를 크게 그린다.
- 데이터가 없는 부위는 "정보 없음"으로 그린다. 상대 옷 값으로 채워 그리지 않는다.

### 5.3 디자인 기준

- ✅ 디자인 기준은 상품 상세 시안이다. 주 버튼은 초록. (10/22)
- ✅ **모든 화면을 상세 시안 토큰으로 통일한다** (디자인 리뷰, 10/27). 파란 `--fit`과 검정 주 버튼을 없앤다.
- ✅ **글자·버튼용 진한 초록을 하나 더 둔다** (10/27). 지금 초록 위 흰 글자 대비가 2.52:1로 기준(4.5:1)에 못 미친다. 넓은 면과 도식은 지금 초록을 유지한다. ⬜ 색 값은 디자이너가 고른다.
- ✅ 초록은 "주 행동"만 뜻한다 (10/27). "내 옷"이나 "비슷해요"를 초록으로 표시하지 않는다(5.2와 함께).

### 5.4 빈 상태

- ✅ 등록 전 비교 예시는 보여 주지 않는다 (10/27). 지금처럼 문구와 첫 등록 쿠폰으로 안내한다.

## 6. 구매와 주문

- ✅ 구매 확정 뒤에 옷장 담기를 묻는다. 반품한 옷은 담지 않는다. (10/22)
- ✅ **주문 상태는 하나의 값으로 관리한다** (엔지니어 리뷰, 10/27). `배송 중 → 배송 완료 → 구매 확정 → 옷장 담김` / `배송 완료 → 반품 신청`. 확정·반품·담기 전에 현재 상태를 확인한다. 지금은 반품 신청한 주문도 알림에서 옷장에 담을 수 있다(버그).
- ✅ **주문에 추천 사이즈, 산 사이즈, 추천 상태를 남긴다.** (10/26)
- ✅ 구매 확정 때 "사이즈가 맞았나요?"는 **이번에는 묻지 않는다.** 10/28 유저 테스트에서 답할 의향을 확인하고 다시 정한다. (10/26)
- ✅ 배송 완료 뒤 정해진 기간이 지나면 자동 확정하고, 다음 앱 실행 때 옷장 담기를 묻는다 (E4, 10/27). ⬜ 기간.
- ✅ 반품과 교환을 나누고, 교환할 때 기준 옷 기준으로 사이즈 추천을 다시 보여 준다 (E3, 10/27). 서비스 핵심과 직접 이어진다.
- ⬜ 장바구니에서 사이즈를 바꿀 때 추천을 보여 줄지 (E8).

## 7. 개인정보와 동의

| 데이터 | 왜 받나 | 상태 |
|---|---|---|
| 옷 치수 | 사이즈 비교 | ✅ 옷장에 처음 들어갈 때 동의를 받는다. 동의하지 않으면 옷장 기능을 쓸 수 없다고 안내한다 (E10, 10/27). 지금은 "선택" 동의인데 동의하지 않아도 제한이 없다 |
| 옷 사진 | 사진 측정, 옷장 표시 | ✅ 보관한다. 옷장 표시에 쓴다 (10/27) |
| 구매내역 캡처 | 상품 찾기 | ✅ 상품을 찾은 뒤 원본은 보관하지 않는다 (10/27). 캡처에는 주문번호·이름 같은 개인정보가 들어간다 |
| 주문 데이터 | 구매 확정, 추천 측정 | ✅ 추천 사이즈를 함께 남긴다(6장) |

- ✅ 사용자가 직접 입력하지 않은 신체·옷 정보는 가져오지 않는다(예: 다른 서비스의 체성분 수치). (멘토링 3회차)
- ⬜ 탈퇴 때 데이터별 삭제·보관 기간. 주문 기록은 법적으로 일정 기간 보관해야 하므로 확인이 필요하다 (E5).

## 8. 측정

- ✅ 정답표로 추천 규칙을 잰다(4.4).
- ✅ 주문에 추천 정보를 남긴다(6장).
- ✅ **핵심 지표:** 같은 그룹 기준 옷이 있는 사용자의 상품 상세 조회 중, 비교가 표시되고 추천 사이즈를 고른 비율 (gstack CEO 리뷰, 10/27). ⬜ 보조 지표 2개(이용과 신뢰가 실제로 생기는지, 잘못된 추천이 늘지 않는지).
- ✅ "반품 감소"를 효과 지표로 내세우지 않는다 (10/27). 실패한 옷은 반품되지 않아서(인터뷰 0/4) 반품률에 효과가 드러나지 않는다. 전환과 재구매 신뢰를 앞세우고, 왜 반품률로 잴 수 없는지를 발표에서 설명한다.
- ✅ 유저 테스트 합격선은 실행 전에 숫자로 정한다 (10/27). 예: 참가자 10명 중 7명 이상이 도움 없이 첫 옷을 등록한다.
